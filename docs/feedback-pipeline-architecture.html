Feedback pipeline

One persona from start to finish: a Youth CSV exported from Mitra, uploaded through the API, stored, and turned into DOTS metadata fields by one LLM call per session. Everything drawn in amber is read from the database when it runs. It is not in code.

The whole path

What happens in each stage

Upload

STEPS 1 TO 5
  • The operator posts the CSV with report_type=feedback, leader_category=Youth, source=mitra. One upload is one persona.
  • The API finds the program and persona and loads the active upload config once. Before anything is stored it checks the file size, the required columns, and that every row has session_type = Youth_Voice.
  • The CSV goes to object storage and a csv_uploads row is written. A delta check against stored sessions sorts each one into new, grown (re-sent in full) or unchanged. Unchanged ones are skipped.
  • One Kafka event per new or grown session, checked against the config's ingestion_schema. A bad session goes to the DLQ topic with its identifiers and never blocks the others. Each event carries the persona and the questionnaire version for the session's start date.

Reads: columns, opening_row, closing_keys, bot_sender_ids, max_csv_upload_bytes, ingestion_schema, questionnaire_versions

Ingest

STEPS 6 TO 9
  • The consumer checks the event again against ingestion_schema (cached for 60 seconds, so a burst does not query per event).
  • It writes submissions, feedback_submissions and feedbacks in one transaction. A session that grew gets its pii_detected reset to NULL and goes back to pending.
  • It reads process_steps. An empty list marks the session success right away, which is the default. Extraction runs only for personas where the step is listed.

Reads: ingestion_schema, process_steps

Trigger

STEP 10
  • The consumer starts ConfigDrivenProcessingWorkflow with the id realtime-<submission>-<tenant> on the Temporal task queue. In batch mode a scheduled sweep starts it for pending sessions instead.
  • The workflow sets the status to processing and runs each listed step by name, with up to 3 attempts per activity.

Extract

STEPS 11 TO 14
  • The activity loads the whole conversation in order, the Youth extraction config, and the prompt named in that config.
  • One call to OpenRouter returns JSON with the persona's fields and a PII flag. Code validates it strictly: values must fit the configured bands or the integer range, placeholders such as "N/A" become not provided, anything else is stored as unmapped with the raw words kept.
  • Code adds a PII backstop: 8 or more digits, an email, an @handle or a URL forces the flag on, whatever the model said.
  • One transaction writes feedback_extracted_data, pii_detected, meta_data.extraction and llm_logs. If the conversation changed during the call, nothing is written and the step retries.

Reads: fields, pii.types, llm, prompt_name, the prompt text

Export

STEP 15
  • A person runs a pivot query: one row per session, one column per DOTS field with a status column beside it.
  • The queries leave out sessions where pii_detected is true or still NULL. Sensitive columns (disability, disability type, household income) stay out of the export until product confirms.

When something goes wrong

Unchanged sessionSkipped at upload. Nothing is published and nothing is written.
Bad session in a fileGoes to the DLQ topic with its identifiers. The other sessions continue.
Config missing or invalidThe event is dead-lettered with a hint to run feedback_config.py migrate and replay it. A stored session is marked failed, not retried in a loop.
Session grew during the model callThe write is refused and the step retries on the new content. The PII flag is never left from older text.
Model or provider errorProvider text is stripped from errors and logs. Temporal retries up to 3 times, then the step fails.
Very long respondent messageOver 20,000 characters: no model call, the session is flagged PII and its fields are stored as unmapped.
