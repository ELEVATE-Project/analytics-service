# Feedback uploads (Mitra + Google Forms): plan

Status: **proposed, not implemented.** Decisions below were agreed in discussion; open items are listed at the end.

## Context
The One Million Voices (1MV) pilot collects feedback from three personas (youth, general public, parents) through two channels: the Mitra bot (message-level raw conversation export) and Google Forms (one wide row per respondent). Today `POST /v1/upload/` only understands `story` and `discussion` (one CSV row = one submission). We add a third report type, **`feedback`**, so both channels use the same upload API, land in a new `feedbacks` table (one row per question and one per answer), and are driven by per-program configuration that can grow or shrink without a deploy. Per-response meta info lives in `submissions` exactly as for story/discussion. Standardised respondent metadata (age, income, gender, ...) is stored as typed rows in a new table, `feedback_extracted_data`, so it can be filtered and aggregated (range queries, Metabase) without JSON casts.

Code and data findings that shape the plan:
- Everything hangs off a `submissions` row (composite FK `(submission_id, tenant_code)`, cascade delete, status, `session_id` UNIQUE). `analysis_results.statement_id` has no FK, so it can later point at `feedbacks.id`.
- `validate_report_type`, `validate_columns`, `get_kafka_ingestion_schema`, `get_process_config`, `insert_or_update_submission`, `validate_ingestion_schema` all hardcode `story`/`discussion`; `validate_columns` demands an exact column match (contradicts "columns can expand or shrink").
- Story/discussion pattern: `submissions` (core meta) + 1:1 payload table (`story_submissions` / `discussion_submissions`). Their `submission_id` is a platform numeric id and `sessionId` a 32-char token.
- Column types in `submissions`: `id` is a `UUID` primary key generated by Postgres (never set by the code); `submission_id` is `TEXT NOT NULL`; `session_id` is `TEXT UNIQUE`. All other tables join through `(submission_id, tenant_code)`, not `id`. A UUID string therefore fits `submission_id` and `session_id` as is.
- Mitra raw export (`1MV_POC/first-final-mitra-out/table_without_1st_question.csv`, the file this plan is written against): 96,027 rows / 3,013 sessions (Parent bot 88: 2,412; General bot 89: 286; Youth bot 90: 315), 2,364 `COMPLETED` and 649 `IN_PROGRESS`; languages kn 1,690, hi 826, en 481, ta/te/or 16. Columns: `bot_id, bot_name, session_status, session, submission_id, language, sequence, conversation_row_id, message, translated_message, created_at, updated_at, stage, receiver_id, sender_id, audio_file, file_url, other_params`.
  - Identity: `submission_id` (6-digit chat-session id) and `session` (32-char token) are on every row and map 1:1 (3,013 each). `sequence` is clean 1..n in every session. `bot_id`, `session_status` and `language` are constant within a session.
  - Completion: `session_status` is `COMPLETED` exactly when the session has a `THANK_YOU` / `CLOSING` row (true for all 3,013 sessions).
  - Text columns: bot rows (`sender_id` 1) have `message` = English and `translated_message` = language shown; respondent rows have `message` = original and `translated_message` = English (empty for English sessions). Respondents are `sender_id` 120 except in 9 sessions (1598, 1611, 1623), so any sender other than 1 is a respondent.
  - First question: still **not** logged. A session starts with the respondent's answer to `STATE_IDENTIFICATION` (Parent) or `AGE_IDENTIFICATION` (General, Youth); the service synthesises that question from the catalog, at sequence 1 (every CSV sequence is shifted by +1; see Sequence numbering). The sibling `table_with_1st_question.csv` adds a placeholder row per session (blank sender, stage and `created_at`, non-unique `conversation_row_id`); it is not used.
- Gotchas: pandas `read_csv` defaults turn the answers "NA"/"None" into NaN (4 in the current file: two "NA", two "None"); `created_at` carries `+05:30` on every row; 49.4 MB for 3,013 sessions vs a 10 MB cap (Parent alone is 43 MB); `other_params` (LLM reasoning JSON), `file_url` (S3 paths) and `audio_file` are ignored and never stored; `process_csv_inline` fabricates uuid4 program/leader ids when the lookup fails; in real-time mode an empty `PROCESS_CONFIG_*` leaves a submission `pending` forever (batch mode marks it `success`); the consumer skips a duplicate `create`, so a session uploaded in progress would never receive later messages.

## Decisions
Agreed: (1) `tenant_code` stays the org (e.g. `mitra`), a `source` column (`mitra` | `google_forms`) is added; (2) one `submissions` row per session, so `submission_id` is never null; (3) per-program upload configuration in two **database tables**, `config` (what the config is for: source, type, program, bot) and `config_version` (the versioned JSON settings); (4) `feedbacks` stores `message` and `translated_message`; (5) identifiers as in the next section (Mitra sends both ids in the CSV; for Google Forms the service generates a UUIDv4 after the upload and keeps the response's natural key in a unique `source_ref` column); (6) a 1:1 `feedback_submissions` payload table; (7) Google Forms conversion happens **inside the system**: the original column-based CSV is uploaded, stored untouched in the bucket, and reshaped into question/answer rows by an adapter driven by the DB config (no offline or manual step); (8) uploads are incremental: only the delta is processed and inserted; (9) standardised respondent metadata lives in a typed child table, `feedback_extracted_data` (one row per extracted value, with numeric, range and category columns), not in a JSON column, so `feedback_submissions` has no `respondent` column; (10) program and persona: one program, `1M Voice`, stored as three `programs` rows, one under each of three leader categories (`Youth`, `Parent`, `General Public`); the persona is the leader category, `leader_category` stays a required upload field, and only names are stored (codes such as `1m_voice` are not, since `programs` and `leader_category` have no code column and existing tables are not altered); (11) one upload is one persona: the Mitra export is split by bot into three files (bot 88 `Parent`, 89 `General Public`, 90 `Youth`), and a file containing another persona's bot is rejected whole; (12) bad sessions are skipped, not fatal: they are pushed to the DLQ topic and reported in `csv_uploads.meta_data`, and the upload still ends `success`, as story and discussion do for skipped rows (section 3, item 2b); (13) the synthesised first question is sequence 1 and every Mitra CSV sequence is shifted by +1, so questions are mostly odd and answers even; `parent_id` is always the deciding factor, never sequence parity; (14) the feedback upload has its own, higher size cap, and story and discussion keep 10 MB; (15) seed rows use fixed UUIDs.

Defaults (to be confirmed): per-session Kafka events; metadata extraction is rule-based at ingestion (Phase 3), with an LLM fallback only as a later Temporal step; the `extraction_method` column stays; upsert by `(submission_id, tenant_code, sequence)` so in-progress sessions can be re-uploaded.

## Identifiers
| | `submission_id` (TEXT) | `session_id` (TEXT) |
|---|---|---|
| Mitra | `chatbot_chatsession.id` (e.g. `183735`), **a column in the uploaded CSV** | the session token, **also a column in the CSV** |
| Google Forms | UUIDv4 generated by the analytics service after the upload | the same value as `submission_id` |

- **Mitra:** the export carries `submission_id` (= `chatbot_chatsession.id`, e.g. `184884`) and `session` (the token) on every row. Both columns are **required** in the Mitra upload format (no fallback), so a bad export is rejected at the boundary. `table_without_1st_question.csv` already has both (3,013 sessions, 1:1, none blank). Uniqueness is `(submission_id, session_id, tenant_code)`; chat-session ids are 6 digits and story ids about 4, so a clash is very unlikely.
- **Google Forms:** the sheet export has no response id, so after the upload the service generates a **UUIDv4**, like every other id the database or service creates, and saves it in `submissions` (`submission_id` and `session_id` carry the same value, one id for one response). A random id cannot recognise a response that arrives again in a later upload, so the response's identity is kept separately as a **natural key in a unique `source_ref` column** on `feedback_submissions` (`UNIQUE (tenant_code, source_ref)`; null for Mitra, whose identity is `(submission_id, sequence)`). Before generating an id the service looks the natural key up: found = already ingested, skip; not found = new response, generate the id and insert.
- Natural key: `<Timestamp>:<answer_hash>`, with the Timestamp normalised to ISO (the export writes e.g. `10/2/2026 10:09:20`, which has no timezone and an ambiguous day/month; accepted formats and the timezone come from config), where `answer_hash` is the SHA-256 of the response's non-blank answers as sorted `(question_key, normalised answer)` pairs (trimmed, whitespace collapsed, Timestamp excluded). Hashing by `question_key` and skipping blank cells keeps the hash stable if the form later gains a new question or a header is reworded. Timestamp alone is not enough: in the Karnataka export 27 of 220 responses share a second (12 pairs, 1 triple), always with different answers. The hash tells them apart and works for cumulative and for delta-only exports. No form code is part of the key or stored on the response: forms and personas have different question sets, so a collision needs the same second and identical answers on the same question keys, which is a double submit and is handled as described under Known limits. The config version and form definition used for a conversion are recorded in `csv_uploads.meta_data`.
- Generating ids is explicit and config-declared (`id_strategy: generate_uuid4` for source `google_forms`), for Google Forms only. The service still never silently invents a missing id for Mitra: if a Mitra row has no `session` or `submission_id`, the upload is rejected.
- Known limits: two responses with identical answers in the same second count as one (practically a double submit; reported as collapsed); an answer edited in the sheet changes the hash and would arrive as a new response. Optional later upgrade: an Apps Script `onFormSubmit` trigger writing a UUID into each response row; if a UUID column is present it becomes the `source_ref` instead of the hash.

## What goes in `submissions` (same as story/discussion)
| Column | Value for feedback |
|---|---|
| `submission_id`, `session_id`, `tenant_code`, `submission_type='feedback'` | per the table above / `mitra` / `feedback` |
| `program_id`, `leader_id` | resolved from `program_name` (`1M Voice`) + `leader_category` (the persona), looked up by name and tenant (must be seeded) |
| `submission_date` | session start (first message time, or the Google Forms Timestamp) |
| `state`, `district` | from the respondent's state/district answers via config aliases in Phase 1 (null if unrecognised); full standardisation into `feedback_extracted_data` in Phase 3 |
| `status` | processing status as today (`pending` / `processing` / `success` / `failed`) |
| `user_id`, `user_name`, `role`, `organization` | null (Mitra's respondent `sender_id` is 120 in all but 9 sessions, so it is not a user id; persona is carried by the leader category, and so by the program row) |

Type-specific fields go in a new 1:1 payload table, like `story_submissions`, so `submissions` is not touched:
```sql
CREATE TABLE feedback_submissions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  submission_id TEXT NOT NULL, tenant_code TEXT NOT NULL,
  source TEXT NOT NULL,                 -- 'mitra' | 'google_forms'
  language TEXT,
  completion_status TEXT NOT NULL CHECK (completion_status IN ('COMPLETED','IN_PROGRESS')),
  source_ref TEXT,                      -- natural key of the response; set for google_forms, null for mitra
  meta_data JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  FOREIGN KEY (submission_id, tenant_code) REFERENCES submissions(submission_id, tenant_code) ON DELETE CASCADE,
  UNIQUE (submission_id, tenant_code),
  UNIQUE (tenant_code, source_ref)      -- NULLs are allowed; guarantees a Google Forms response is stored once
);
```
`completion_status` is stored (updated on re-upload): Mitra = the CSV's `session_status` of that session, taken as is (a session whose rows disagree on it is rejected, and so is a value other than `COMPLETED` / `IN_PROGRESS`); Google Forms = `COMPLETED` by config default (`default_completion`).

## Target flow
```
Mitra raw CSV (long) ───────────────┐
Google Forms CSV (wide, original) ──┤   both uploaded exactly as they are
                                    ▼
POST /v1/upload/ (report_type=feedback, program_name=1M Voice, leader_category=<persona>, tenant_code, source)
  → file-level checks, file rejected whole with an error and nothing stored: parse (dtype=str,
    keep_default_na=False), required columns, bot_id vs the program's config rows, program + leader exist
  → csv_uploads row + original file kept untouched in the bucket (existing)
  → load the active config_version for (source, program, bot_id in the file) (DB)
  → adapter: Mitra = read the long rows; Google Forms = reshape each wide row into question/answer rows
  → delta check (skip what is already stored) → one event per new or changed session;
    a malformed session is skipped, pushed to the DLQ and listed in csv_uploads.meta_data (upload still ends success)
  → Kafka (existing topic + DLQ) → consumer
  → submissions + feedback_submissions + feedbacks (one transaction, upsert by sequence)
  → Phase 3: rule-based extraction of metadata answers into feedback_extracted_data (same transaction)
```

## Incremental uploads (delta only)
Mitra and Google Forms exports arrive repeatedly over time, as cumulative files or as new rows only. The existing file-level duplicate check (same name and size) stays, but it is not the delta mechanism. The delta is decided per message and per response, before anything is published to Kafka:
- **Mitra:** identity is `(submission_id, sequence)` using the stored sequence (CSV sequence + 1, applied to every file, so a tail-only export lines up with what is stored). The service reads the existing sequences and `completion_status` for the sessions in the file and publishes only sessions with new messages, carrying only the new rows. A session with no new sequences and the same `session_status` is skipped; a changed `session_status` (e.g. `IN_PROGRESS` to `COMPLETED`) updates `completion_status`. An export holding only the tail of a session may start with an answer whose question is already stored, so the parent link is taken from the stored rows.
- **Google Forms:** identity is `source_ref` (see Identifiers). Responses already stored are skipped; only new ones are converted and inserted.
- **Safety net:** the database constraints (`UNIQUE (submission_id, tenant_code, sequence)`, `UNIQUE (tenant_code, source_ref)`) and idempotent upserts make a repeated or overlapping upload harmless even if the pre-check races; the consumer processes one message at a time.
- **Report:** each upload records rows read, sessions new / updated / unchanged, and collapsed duplicates in `csv_uploads.meta_data`.

## 1. Data model (append to `schema.sql`; new tables only, no ALTER of existing tables)
`db.py` executes `schema.sql` at startup with `IF NOT EXISTS` injected, so new `CREATE TABLE` blocks are picked up automatically.

```sql
CREATE TABLE feedbacks (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  submission_id        TEXT NOT NULL,
  tenant_code          TEXT NOT NULL,
  session_id           TEXT NOT NULL,
  program_id           UUID REFERENCES programs(id) ON DELETE SET NULL,
  source               TEXT NOT NULL,
  submission_type      TEXT NOT NULL DEFAULT 'feedback',
  sequence             INT  NOT NULL,                    -- Mitra: CSV sequence + 1 (1 = synthesised first question); Google Forms: 1..n
  is_follow_up         BOOLEAN NOT NULL DEFAULT FALSE,   -- bot probe / follow-up question
  question_key         TEXT,                             -- canonical question id (Mitra stage), shared across sources
  parent_id            UUID REFERENCES feedbacks(id) ON DELETE CASCADE,   -- answer -> its question row; NULL for questions and the closing message
  message              TEXT NOT NULL,                    -- as spoken in the conversation language
  translated_message   TEXT,                             -- English
  language             TEXT,
  message_at           TIMESTAMPTZ,                      -- when it was said (from the CSV)
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  FOREIGN KEY (submission_id, tenant_code) REFERENCES submissions(submission_id, tenant_code) ON DELETE CASCADE,
  UNIQUE (submission_id, tenant_code, sequence)
);
-- indexes: (program_id, question_key), (parent_id), (source)
```
There is no `role` column: a row is an answer when `parent_id` is set, and a question (or the closing message, recognisable by its `question_key`, `THANK_YOU` / `CLOSING`) when it is NULL. Beyond the minimal column set requested: `is_follow_up`, `question_key` (canonical question across sources; `parent_id` alone cannot group answers across Mitra and Google Forms), `message_at` (conversation time; `created_at` stays DB insert time per repo convention).

Sequence numbering: for Mitra the stored `sequence` is the CSV sequence + 1, and the synthesised first question is sequence 1 (it is added only when the session's CSV starts at sequence 1; a tail-only export adds none). The stored value is therefore not the file's value (the file's value is stored minus 1), and the rule is applied to every Mitra file so identity stays stable across uploads. Google Forms rows are numbered 1..n, a question row followed by its answer row. In 3,006 of the 3,013 sessions in the current export questions fall on odd and answers on even sequences, but 7 sessions have two bot messages or two respondent messages in a row, so parity is only a convention: `parent_id` alone decides whether a row is an answer.

Text invariant, normalised at ingestion: `message` = what was said in the conversation language, `translated_message` = English. This is not a straight copy of the CSV columns of the same name, because Mitra bot rows carry them the other way round. Bot rows: `message` = CSV `translated_message`, `translated_message` = CSV `message`; respondent rows: copied as is. If the conversation-language text is empty, `message` takes the English text (never NULL); in English sessions both columns hold the same text; in other languages a missing English text stays NULL (3 Hindi rows today).

Typed metadata (created in Phase 3). One row per extracted value from a metadata answer (age, gender, income, relationship, ...), so range filters, aggregations and Metabase filters work on real numeric and category columns instead of JSON:
```sql
CREATE TABLE feedback_extracted_data (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  submission_id     TEXT NOT NULL,
  tenant_code       TEXT NOT NULL,
  feedback_id       UUID NOT NULL REFERENCES feedbacks(id) ON DELETE CASCADE,   -- the answer row this came from
  question_key      TEXT NOT NULL,                  -- 'AGE_IDENTIFICATION', 'HOUSEHOLD_INCOME', ...
  value_index       SMALLINT NOT NULL DEFAULT 0,    -- 0 for single answers; 0,1,2... for multi-select
  data_type         TEXT NOT NULL CHECK (data_type IN ('numeric','categorical','range')),
  raw_value         TEXT NOT NULL,                  -- the answer as given: "10L", "twenty five", "3 to 8 lakh"
  numeric_value     NUMERIC,                        -- 25, 1000000
  range_min         NUMERIC,                        -- 300000
  range_max         NUMERIC,                        -- 800000
  category_value    TEXT,                           -- standardised band or choice: '3L - 8L', 'female', 'unknown'
  unit              TEXT,                           -- 'years', 'INR'
  extraction_method TEXT NOT NULL CHECK (extraction_method IN ('rule','llm','manual')),
  confidence_score  DOUBLE PRECISION,               -- NULL for rule-based
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  FOREIGN KEY (submission_id, tenant_code) REFERENCES submissions(submission_id, tenant_code) ON DELETE CASCADE,
  UNIQUE (submission_id, tenant_code, question_key, value_index),
  CHECK (numeric_value IS NOT NULL OR range_min IS NOT NULL OR range_max IS NOT NULL OR category_value IS NOT NULL),
  CHECK (range_min IS NULL OR range_max IS NULL OR range_min <= range_max)
);
-- indexes: (tenant_code, question_key, numeric_value) WHERE numeric_value IS NOT NULL;
--          (tenant_code, question_key, category_value) WHERE category_value IS NOT NULL;
--          (tenant_code, question_key, range_min, range_max) WHERE range_min IS NOT NULL;
--          (feedback_id) for cascade deletes. The unique key's index already serves joins on (submission_id, tenant_code).
```
A numeric answer fills `numeric_value` and `unit`; a banded answer fills `range_min` / `range_max`; a choice fills `category_value`. An unusable answer ("don't know", "skip") is kept with `category_value = 'unknown'` and NULL numbers, so range queries ignore it without cast errors. `question_key`, `submission_id` and `tenant_code` repeat what the answer row carries; the service fills them from that row, and they are here so the indexes and tenant-scoped filters need no join. The unique key makes re-extraction an upsert and `value_index` handles multi-select answers. `extraction_method` (`rule` | `llm` | `manual`) and `confidence_score` tell rule-based values from LLM ones. Metabase reads one view (or materialised view) per persona that pivots these rows into one flat row per response, joined on `(submission_id, tenant_code)`, for example `MAX(numeric_value) FILTER (WHERE question_key = 'AGE_IDENTIFICATION') AS age`.

```sql
CREATE TABLE config (                    -- what to process and how to read it; not the LLM prompts (those stay in prompts/prompt_version)
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config_source TEXT NOT NULL CHECK (config_source IN ('mitra','google_forms')),
  name TEXT NOT NULL,                    -- e.g. 'Youth bot CSV validator'
  config_type TEXT NOT NULL,             -- 'feedback_upload' for now (story/discussion keep env config)
  program_id UUID REFERENCES programs(id) ON DELETE CASCADE,   -- NULL = default for the source and type
  tenant_code TEXT NOT NULL REFERENCES tenant(code),
  leader_id UUID REFERENCES leader_category(id) ON DELETE SET NULL,   -- optional; NULL for the feedback bots
  bot_id TEXT,                           -- Mitra bot id the config applies to; NULL for Google Forms
  bot_name TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- one config per (source, type, program, bot): unique index on
--   (config_source, config_type, COALESCE(program_id, zero-uuid), COALESCE(bot_id, ''))

CREATE TABLE config_version (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config_id UUID NOT NULL REFERENCES config(id) ON DELETE CASCADE,
  version INT NOT NULL DEFAULT 1,
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  config JSONB NOT NULL,                 -- columns, sender rule, message_map, questions catalog ...
  created_by TEXT, change_note TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (config_id, version)
);
-- one active version per config: unique index on (config_id) WHERE is_active
```
Resolution: for a Mitra upload, the active `config_version` of the `config` row matching `(config_source, config_type, program_id, bot_id from the file)`; a file whose `bot_id` has no config row for the program is rejected whole (a file-level check; e.g. `90` uploaded under `Parent`). For Google Forms, the row with `bot_id` NULL for the program, else the active default (`program_id` NULL). `leader_id` on `config` is optional metadata; `submissions.leader_id` still comes from the upload's `leader_category`. Each `config_version.config` holds: `required` / `optional` / `ignored` columns and `aliases`; `ignore_extra_columns: true`; column roles (`submission_id`, `session`, `session_status`, `bot_id`, `language` required for Mitra; `layout: wide` and `id_strategy: generate_uuid4` for source `google_forms`, with its `forms` definitions (section 4); `sequence`, `message`, `translated_message`, `question_key`, `created_at` with accepted datetime formats and a fallback timezone for values without an offset); sender rule (`bot_sender_ids: ["1"]` = bot question, any other sender = respondent answer; it only decides `parent_id`, nothing is stored for it); the per-sender `message_map`; `default_completion` for Google Forms (Mitra reads `session_status`); the `questions` catalog (`key`, English `text`, `kind` = metadata | open, `metadata_field`; for metadata questions the extraction rule: `data_type` (numeric | range | categorical), `unit`, the band list and aliases; state/district alias lists). The catalog lets us synthesise the unlogged first question and, in Phase 3, extract typed metadata. Seed inserts must be `ON CONFLICT DO NOTHING` (never overwrite), otherwise the startup seed would clobber edits made without a deploy. `programs` and `leader_category` have no unique key on name, so a name-based conflict would not dedupe; the seed rows for `leader_category`, `programs` and `config` therefore use fixed UUIDs (`ON CONFLICT (id) DO NOTHING`), and `config_version` rows are keyed by `(config_id, version)`.

## 2. Canonical upload format
- Mitra raw CSV is accepted as is (`table_without_1st_question.csv` format). Required (config-driven): `bot_id`, `session_status`, `session`, `submission_id`, `language`, `sequence`, `message`, `created_at`, `stage`, `sender_id`; optional: `translated_message`, `bot_name`, `conversation_row_id`, `receiver_id`, `updated_at`; ignored and never stored: `audio_file`, `file_url`, `other_params`. Any other extra column is ignored too. `source` comes from the form field, not the CSV.
- Google Forms is uploaded **as the original wide CSV**; the service reshapes it into the same canonical question/answer records (section 4). No manual conversion step.
- New optional form field `source` (`mitra` default | `google_forms`), validated against the program's config rows.
- `program_name` + `leader_category` must match **seeded** rows: `program_name` = `1M Voice`, `leader_category` = `Youth`, `Parent` or `General Public` (names only; the three programs, one per leader category, are seeded with fixed UUIDs). For feedback, reject with a clear error instead of fabricating uuid4 ids when the lookup fails (file-level check, item 2b).

## 3. Upload service and consumer
Files: `app/api/validators/uploads.py`, `app/api/routes/uploads.py`, `app/api/services/uploads.py`, new `app/api/services/feedback_uploads.py`, `app/config.py`, `app/services/ingestion_validation.py`, `app/kafka/consumer.py`, `app/database/operations.py`, `app/database/db.py` (seed hook), `schema.sql`.
1. `validate_report_type` accepts `feedback`; `validate_columns` gets a config-driven mode (required/optional, extras allowed). Story/discussion behaviour unchanged.
2. `process_csv_inline` branches on `report_type`. `feedback_uploads.py`: load the active `config_version` for the program and the file's `bot_id`, `pd.read_csv(dtype=str, keep_default_na=False)`, session checks (session present, sequence integer and unique within the session, message non-empty, `bot_id` / `session_status` / `language` constant within the session; item 2b), sort by sequence, derive `is_follow_up` / `question_key` / parent link (an answer's parent is the nearest preceding question row, so multi-message answers share one parent), apply the language mapping, synthesise the missing first question from the catalog at sequence 1 and shift the CSV sequences by +1 (its key is the stage of the session's first row; only when the session's CSV starts at sequence 1), take `completion_status` from `session_status`, build one event per session, validate, publish via the existing `_push_rows_sync`. Reuse `get_csv_value` aliasing, `format_datetime`, `csv_uploads` status handling (`on_hold` on failure; per-session errors in `meta_data`).
2b. Two tiers of validation, following the story/discussion flow (file problems are rejected up front, bad rows are skipped):
   - **File level**, in `handle_upload` (synchronous; an error is returned and nothing is stored): feedback gets its own parse (`dtype=str`, `keep_default_na=False`; the existing default parse would turn "NA" / "None" answers into NaN), then checks the required columns (config-driven), that every row's `bot_id` has a `config` row for the program (a file holding another persona's bot is rejected whole, so a mixed export is never half-loaded), and that `program_name` + `leader_category` exist for the tenant (feedback looks them up by name and `tenant_code`, because the current query matches the leader name only; an unknown value is an error, never a fabricated id). The existing same-file duplicate check (program, leader, type, name, size) stays.
   - **Session level**, in `process_csv_inline`: a session that fails (blank `submission_id` / `session`; `sequence` missing, duplicate or not an integer; empty message; `session_status` differing within the session or not `COMPLETED` / `IN_PROGRESS`; failed event schema check) is skipped and pushed to the DLQ topic with its `submissionId`, `sessionId` and the problems. It is listed in `csv_uploads.meta_data` (`rows_pushed` = sessions published, `sessions_skipped`, and the error list under `schema_validation_errors`, the key story/discussion already use). The upload still ends `success`; `on_hold` stays for a fetch or Kafka publish failure, exactly as today. Sending skipped sessions to the DLQ is new behaviour (today a skipped row is only logged and listed). A corrected file is uploaded again and the delta check adds only what is missing.
3. Event: standard envelope (`submissionId`, `submissionType='feedback'`, `sessionId`, `tenantCode`, `eventType`, `eventPublishedAt`, `tags` with program/leader ids, state, district, `source`) and `data` = `{source, language, completionStatus, submissionDate, messages[]}` with `messages[]` = `{sequence, questionKey, isFollowUp, message, translatedMessage, messageAt, parentSequence}`.
4. Validation at the boundary: `FEEDBACK_KAFKA_SCHEMA` (same env pattern); `validate_ingestion_schema` recognises `feedback` and checks array elements (each message has sequence and message; at least one message has a `parentSequence`, i.e. at least one answer). State/district are optional (respondents skip them). Bad sessions go to the DLQ with identifiers.
   - Identifier step (before building events): for Mitra, read `submission_id` and `session` straight from the CSV (reject the file if either column is missing, or any row has it empty). For `source=google_forms` (`id_strategy: generate_uuid4`), compute each response's natural key, look up `feedback_submissions.source_ref`, skip known responses, and for new ones set `submission_id = session_id = str(uuid4())` and store the key in `source_ref`.
   - Delta check: as described under Incremental uploads; only new or changed sessions are published.
5. Consumer + `insert_or_update_submission` feedback branch, one transaction: upsert `submissions` and `feedback_submissions`, then upsert `feedbacks` rows `ON CONFLICT (submission_id, tenant_code, sequence) DO UPDATE` (keeps row ids so later `analysis_results` links survive; updates only when text changed), then a second pass sets `parent_id` from `parentSequence`. For feedback, a `create` on an existing session reconciles instead of skipping, so a re-upload of a grown session adds only the new messages and can flip `IN_PROGRESS` to `COMPLETED` (from the incoming `session_status`). `delete` already cascades.
6. Add `PROCESS_CONFIG_FEEDBACK` (empty in Phase 1). In real-time mode, when a type has no steps, mark the submission `success` at ingestion so both processing modes agree.
6b. Extraction (Phase 3): for each answer row whose `question_key` is a metadata question in the catalog, a rule-based extractor writes `feedback_extracted_data` rows in the consumer's transaction, as an upsert on `(submission_id, tenant_code, question_key, value_index)`. An answer the rules cannot parse is stored with `category_value = 'unknown'` and the raw text; it never fails ingestion. An LLM fallback for unresolved answers is a later Temporal step (`extraction_method = 'llm'`, with `confidence_score`); it is not part of the first cut because it would send children's answers to an external model.
7. Size: the feedback report type gets its own, higher cap (set in `app/config.py`); story and discussion keep 10 MB. The value must exceed the largest persona file (Parent is about 43 MB today) with headroom for growth. The place the cap is enforced, any proxy body limit and the request timeout are checked in Phase 1, since the file is parsed in the request. A persona file is uploaded whole, so the 7-way split is gone: 3 uploads, one per persona. Dropping `other_params`, `file_url` and `audio_file` from the export would cut it from 49 MB to 35 MB (optional). Chunked upload stays a later scale item.

## 4. Google Forms adapter (inside the service)
- Input: the original wide CSV, uploaded as is and kept untouched in the bucket. The program's Google Forms `config_version` declares `layout: wide`, the Timestamp column, and a definition per form: an internal form code (a config key only, not stored on the response), the header-to-`question_key` / English-text map (seeded from `1MV_POC/1MV_questions_by_source.csv`) and the question kind. The service picks the form definition from the CSV headers (how it picks is an open item) and rejects the file, listing the unmapped headers, if it matches none. In scope: the launch instruments (General Public, Parents, Youth English launch, Karnataka bilingual); pilot and age-banded drafts are simply not configured. The `config_version.id` used is recorded in `csv_uploads.meta_data`, so a conversion can be reproduced.
- Output per response: for each non-blank cell a question row (English header text, `question_key`) followed by an answer row; `sequence` 1..n; `message_at` = the form Timestamp (accepted formats and timezone come from the config). Blank cells are skipped. Bilingual headers keep the English part. Kannada answers go in `message` with empty `translated_message` (translation later). The output feeds the same event builder as Mitra, so everything downstream is identical.
- Identity: natural key and UUIDv4 as described under Identifiers; completion is `COMPLETED` by config default.
